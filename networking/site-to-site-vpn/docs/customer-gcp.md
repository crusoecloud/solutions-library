# Customer side: GCP HA VPN

How a customer builds the GCP side against an already-deployed Crusoe
endpoint. This is the manual/production path; `terraform/gcp/` is our own
dev/test module that automates the same steps.

## What you need from the Crusoe operator

Everything comes from `handoff.txt` (generated by the Crusoe apply — no
secrets in it):

| handoff.txt value | Used for |
|---|---|
| Crusoe VPN endpoint public IP(s) | External VPN gateway interface IP(s) |
| Crusoe BGP ASN | Peer ASN on each BGP session |
| Crusoe advertised CIDRs | What you'll learn via BGP (for firewall planning) |
| Per tunnel: inside CIDR (/30) | Cloud Router interface IP range |
| Per tunnel: "your BGP IP" / "Crusoe BGP IP" | Your Cloud Router interface IP / the BGP peer address |
| Per tunnel: "Crusoe endpoint public IP" | Which external-gateway interface this tunnel targets (matters for dual-VM HA) |

**PSK convention: the Crusoe operator generates and sets the PSKs** (GCP lets
you choose the shared secret, unlike AWS). Receive them out-of-band — a
secret manager entry or a one-time link, never email or chat. One PSK per
tunnel.

## Topology

GCP HA VPN always creates a gateway with **two interfaces (two public IPs)**
and requires **two tunnels** for its SLA. Both tunnels land on Crusoe:

- Crusoe `ha_mode = "single"` → external VPN gateway with **1 interface**
  (redundancy type `SINGLE_IP_INTERNALLY_REDUNDANT`); both GCP tunnels target
  the same Crusoe IP.
- Crusoe `ha_mode = "dual"` → external VPN gateway with **2 interfaces**
  (`TWO_IPS_REDUNDANCY`), one per Crusoe VM; tunnel N targets interface N.
  Use the per-tunnel "Crusoe endpoint public IP" line in `handoff.txt` to map
  tunnels to interfaces.

## Steps (gcloud)

Console path: *Network Connectivity → VPN → Create VPN connection → HA VPN*;
the gcloud commands below map 1:1.

```bash
PROJECT=<your-project> REGION=<region> NETWORK=<your-vpc>

# 1. HA VPN gateway (gets two public IPs)
gcloud compute vpn-gateways create crusoe-ha-gw \
  --project=$PROJECT --region=$REGION --network=$NETWORK

# 2. External (peer) VPN gateway representing Crusoe
# single Crusoe VM:
gcloud compute external-vpn-gateways create crusoe-peer \
  --project=$PROJECT \
  --interfaces 0=<CRUSOE_PUBLIC_IP>
# dual Crusoe VMs instead:
#   --interfaces 0=<CRUSOE_IP_VM0>,1=<CRUSOE_IP_VM1>

# 3. Cloud Router with YOUR private ASN
#    (this is the remote_asn the Crusoe side configured — from handoff.txt)
gcloud compute routers create crusoe-router \
  --project=$PROJECT --region=$REGION --network=$NETWORK \
  --asn=<YOUR_ASN>

# 4. Two tunnels, IKEv2, PSKs provided by the Crusoe operator
gcloud compute vpn-tunnels create crusoe-tunnel-0 \
  --project=$PROJECT --region=$REGION \
  --vpn-gateway=crusoe-ha-gw --interface=0 \
  --peer-external-gateway=crusoe-peer --peer-external-gateway-interface=0 \
  --ike-version=2 --shared-secret=<PSK_TUNNEL_A> \
  --router=crusoe-router
gcloud compute vpn-tunnels create crusoe-tunnel-1 \
  --project=$PROJECT --region=$REGION \
  --vpn-gateway=crusoe-ha-gw --interface=1 \
  --peer-external-gateway=crusoe-peer \
  # 1 for dual-VM HA
  --peer-external-gateway-interface=0 \
  --ike-version=2 --shared-secret=<PSK_TUNNEL_B> \
  --router=crusoe-router

# 5. BGP: one router interface + peer per tunnel, on the /30s from handoff.txt
# tunnel-a example: inside CIDR 169.254.21.0/30, your IP .1, Crusoe .2
gcloud compute routers add-interface crusoe-router \
  --project=$PROJECT --region=$REGION \
  --interface-name=if-tunnel-0 --vpn-tunnel=crusoe-tunnel-0 \
  --ip-address=169.254.21.1 --mask-length=30
gcloud compute routers add-bgp-peer crusoe-router \
  --project=$PROJECT --region=$REGION \
  --peer-name=peer-tunnel-0 --interface=if-tunnel-0 \
  --peer-ip-address=169.254.21.2 --peer-asn=<CRUSOE_ASN>
# repeat for tunnel 1 with its /30
```

The exact interface IPs per tunnel are in `handoff.txt` ("your BGP IP" is the
Cloud Router side; "Crusoe BGP IP" is the peer).

## Advertised routes

By default the Cloud Router advertises the subnets of the VPC. That is
usually what you want — the Crusoe side filters inbound prefixes to the
agreed `customer_cidrs`, so **anything you advertise beyond that list is
dropped**. If you use custom advertisement, advertise exactly the CIDRs you
agreed with the Crusoe operator:

```bash
gcloud compute routers update-bgp-peer crusoe-router \
  --peer-name=peer-tunnel-0 \
  --advertisement-mode=CUSTOM --set-advertisement-ranges=10.200.0.0/16
```

Also add VPC firewall rules permitting the Crusoe CIDRs into whatever you
intend to expose (the tunnel delivers packets; your firewall still decides).

## Sending crusoe-bound values back

Nothing — GCP HA VPN gateway IPs must be known **before** the Crusoe apply
(they are `tunnels[*].peer_public_ip`). Typical flow: create the HA VPN
gateway first (step 1), send the two interface IPs and your ASN to the Crusoe
operator, receive `handoff.txt` + PSKs, then finish steps 2–5.

## Verify

```bash
gcloud compute vpn-tunnels describe crusoe-tunnel-0 --region=$REGION \
  --format='value(status,detailedStatus)'        # ESTABLISHED
gcloud compute routers get-status crusoe-router --region=$REGION \
  --format='value(result.bgpPeerStatus[].state)' # Established, Established
```

Both tunnels `ESTABLISHED`, both BGP sessions `Established`, and the Crusoe
CIDRs present as dynamic routes. If not, work the decision tree in
[docs/runbook.md](runbook.md#6-troubleshoot-decision-tree) together with the
Crusoe operator — most failures (proposal mismatch, PSK, wrong peer IP) show
symptoms on both ends.
